## Steps

Let's do this one step at a time, mainly for my own sake in implementing and testing the code. We'll start with "Chunking".

### Chunking

Using ["output"]["html_tokens_per_page"] fromt `config.toml`, divide the text thus:

- Since we're working with *tokenized* editions, we will assume that the natural unit can be identified by dropping the last two elements (`.token.1`) from the CTS-URN. **Except for Drama…**
- For drama, the natural unit is complicated: speech, but also line.
- For *prose* and *poetry*, we can chunk by natural unit, aiming for `tokens_per_page`, but preferring to keep natural units together. 
- In a prose text like Herodotus (cited by book/section), we'll chunk by section, unless a section contains fewer than `tokens_per_page`, in which case we'll also grab the next one.
- In the case of poetry, likewise. We grab lines until we have `tokens_per_page`, but always including a whole line, even if that means exceeding `tokens_per_page` a little.
- In the case of drama, we always want to keep lines intact. Those will be cited by the first (left-most) component of the citation-element in the CTS-URN, *e.g.* `urn:cts:greekLit:tlg0019.tlg009.fu.sp:1`. In our editions, the second element indicates the "speech"; this is useful when a single poetic line involes more than one speaker:

	urn:cts:greekLit:tlg0019.tlg009.fu.sp:7.1.speaker#Διόνυσος
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:7.1.text#θαρρῶν γε· μόνον ἐκεῖνʼ ὅπως μὴ ʼρεῖς,
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:7.2.speaker#Ξανθίας
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:7.2.text#τὸ τί;

- But we can *also* define "speech" as "many lines in a row from the same speaker":

	urn:cts:greekLit:tlg0019.tlg009.fu.sp:209.1.speaker#Βάτραχοι
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:209.1.text#βρεκεκεκὲξ κοὰξ κοάξ,
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:210.1.speaker#Βάτραχοι
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:210.1.text#βρεκεκεκὲξ κοὰξ κοάξ.
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:211.1.speaker#Βάτραχοι
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:211.1.text#λιμναῖα κρηνῶν τέκνα,
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:212.1.speaker#Βάτραχοι
	urn:cts:greekLit:tlg0019.tlg009.fu.sp:212.1.text#ξύναυλον ὕμνων βοὰν

- So we will chunk by line, but prefer to keep speeches—many lines from the same speaker—intact, even if that means exceeding `tokens_per_page`. 

I would like to separate the chunking-function cleanly, having it write `.txt` files for each chunk (CTS-URN + \t + text) into `["output"]["html_temp_dir"]`, specified in `config.toml`. Those might be useful to have, anyway. We can proceed from those files.

### Site Structure and navigation

The html pages for this text's site will go in `["output"]["html_output_dir"] / ["input"]["file_name"] / "pages"` for html files.
, one html file for each chunk. The files should be named with `["input"]["filename"]` + a citation-range + `.html`, based on the chunk.

That is, if one chunk starts with `urn:cts:greekLit:tlg0019.tlg009.fu.sp:209` and ends with `urn:cts:greekLit:tlg0019.tlg009.fu.sp:239`, the filename would be `Aristophanes_Frogs_209-239.html`.

If a chunk starts with `urn:cts:greekLit:tlg0016.tlg001.grc:1.0` and ends with `urn:cts:greekLit:tlg0016.tlg001.grc:1.1`, the filename would be `Herodotus_1.0-1.1.html`. If it contains only `urn:cts:greekLit:tlg0016.tlg001.grc:1.2`, the filename should be `Herodotus_1.2.html`.

(stuff about the html template)

There should be an `index.html` file in that same directory, with some kind of table of contents. 

The function for generating the Table of Contents should be cleanly separated, since there will probably be usability considerations that we want to tweak. For example, a TOC for the Herodotus will be very, very long, and we might want the option to include collapsing it by book.

Each page should have forward-and-back navigation, as well as a clear link back to the index page. The index page should have a "forward" link that goes to the first chunk. The last page's forward-link should return to the index.

Each page should include a link back up to `html_output_dir`, which will include some `index.html` covering all texts for which HTML editions have been generated.

I have tried to account for all of this in the template files.

### Page Structure

Each page will have three main parts:

- Text-body, showing the text to read.
- A sidebar, for showing information about the text-content (mainly at the token-level, for now).
- A `<div>`, invisible by default, containing data associated with the tokens of the text.

In the text-body, tokens will be displayed, using html and CSS, formatted as readers expect:

- Prose will be in paragraphs, by citable unit.
- Poetry will be in poetic lines.
- Drama will be in poetic lines, with speaker-attribution (but this is tricky… see below).

Each token will be wrapped in an HTML element that contains an ID, its token-level CTS-URN. Something like.

	<span class="text_token" data-ctsurn="urn:cts:greekLit:tlg0013.tlg002.fucex.token:24.0">οὐδὲ<span>

In the invisible data-`<div>`, there will be subordinate `<div>`s 

~~~
  <div class="dramaturg_morphology" data-textUrn="urn:cts:greekLit:tlg0013.tlg002.fucex.token:24.0">
  		[ Stuff from our generated data]
  </div>
~~~

### Future-Proofing Assembly of the Data

As described here, any token will be linked to *all possible* morphological parsings. The reader will have to pick the correct one for the context.

In the near-term, I would like to supplment the general morphology-index, [????], with an "editor's index", with the same format, but including only those parsings that an editor (me, probably) thinks are correct in the present context.

So a subsequent version of this process would check the editor's index, first, to see if there is data specifically chosen for this context, and only after that, resort to the general index.

I say a little more about this in the "Desiderata" section, below.

### Site Functionality and User Interface

The example at <https://furman-university-editions.github.io/Readers/Homeric_Hymns/Demeter_1-50.html> was my unaided work, and while it represents my idea of a useful reading environment, it is less than ideal.

What I want:

- "Zero-friction" reading: The user should get information on any token (where there is information) with as little interaction as possible. `:hover` should reveal, in the sidebar, lexical and morphological information for a word. This is a "peek".
- Because we might want to look closer, or keep one word's data displayed while pointing at other things, a "click" should "lock down" the sidebar, so that information doesn't disappear when the cursor hovers over something else. A subsequent click on the token can "unlock" it.
- The site should be entirely self-contained, able to run locally, albeit with the requirment to run a local server. This is why I've included the whole LSJ lexicon-app in `webapps`.
- I'll make an exception for web-fonts, but these should fail gracefully.
- The reader should get the LSJ short-definitions with a "peek" at the sidebar, but there should be a link to the (local) LSJ lexicon. (See "Desidarata" for my thoughts on a subsequent "prepare publicatin" script.)

Where my earlier attempt is weak:

- Touch-devices don't have `:hover`.
- And in general I gave no thought to formatting for touch or small screens. The `screen-size` thing in CSS is really complicated to me, and I'd love your help.
- In general, you will know best-practices for formatting of sites of this kind. I would like something that hits a happy medium between "traditional" or "Aldine" and "clean and modern", if that is possible ;-).
