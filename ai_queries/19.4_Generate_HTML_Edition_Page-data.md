### Assembling the Data

(Specific filenames are given below. The actual values will come from `config.toml`.)

Using the token-morphology index `data/indexes/Aristophanes_Frogs_morphology_index.tsv`, see if there is one or more index-entries for a given token. If there is, they all will recorded and encoded in `div#textdata`. 

The CITE2-URN in the index should map to the text-specific morphology dictionary, *e.g.* `data/morphology/frogs_morph.cex`. The corresponding entry will have a human-readable description of the morphology, in Markdown, in property `desc` (the second `#`-delimited column in the `#!citedata` block) as well as a CITE2-URN to the lexicon (property `lsj`, col 7). We want both.

With the lexicon URN, we can grab the short-definition from `source-data/dictionaries/lsj_short_defs.tsv`.

If there is more than one index-entry for the token-CTS-URN, we want them all.

All that should go into the data-div for this token in some structured HTML way, keyed to the token-level CTS-URN. Like:

```html
  &lt;div id="morphdata"&gt;
      &lt;div class="morph4token" data-tokenurn="urn:cts:greekLit:tlg0019.tlg009.fu.sp:2.1.text.token.3"&gt;
       &lt;div class="formparsing" data-morphurn="urn:cite2:fufolio:greekmorph.2026a:20260604T0959107277"&gt;
          &lt;!-- We would parse the following Markdown before insertion --&gt;
          **ἀεί**. From **ἀεί**. Adverb. [d--------]. See `urn:cite2:hmt:lsj.chicago_md:n1564`.
       &lt;/div&gt;
       &lt;div class="lsj_shortdef" data-lsjurn="urn:cite2:hmt:lsj.chicago_md:n1564"&gt;
        &lt;a href="{{lsj_url}}" class="shortdeflink"&gt;ἀεί; ever, always; until now; from of old; eternity; immortals; …[2 omitted]… for ever; Et.Gud.z; aevum&lt;/a&gt;
       &lt;/div&gt;
  &lt;/div&gt;
```

I have added `["outut"]["lsj_url"]` as a configuration in `config.toml`.

By default, all of the contents of `div#morphdata` will be hidden by CSS.

For now, we can simply populate `div#morphdata` as described (or if you can think of a more sound way!). 

After that, we can add functionality so that some user-interaction with a token will display the morphological-lexical data associated with that token.

In case it helps with the design at this stage, what follows looks forward a little.

### Future-Proofing Assembly of the Data

As described above any token will be linked to *all possible* morphological parsings. The reader will have to choose the correct one for the context.

In the near-term, I would like to supplement the computed morphology-index, like `data/morphology/frogs_morph.cex`, with an "editor's index", with the same format, but including only those parsings that an editor (me, probably) thinks are correct in the present context.

So a subsequent version of this process would check the editor's index, first, to see if there is data specifically chosen for this context, and only after that, resort to the general index.

I say a little more about this in the "Desiderata" section, below.

### Site Functionality and User Interface

The example at &lt;https://furman-university-editions.github.io/Readers/Homeric_Hymns/Demeter_1-50.html&gt; was my unaided work, and while it represents my idea of a useful reading environment, it is less than ideal.

What I hope for:

- "Zero-friction" reading: The user should get information on any token (where there is information) with as little interaction as possible. `:hover` should reveal, in a sidebar, lexical and morphological information for a word. This is a "peek".

&gt; I believe that in the earlier version, I didn't have a special "sidebar-div", but just left a generous right-hand margin next to the text, and the morphological information, when called up, was programatically made visible and displayed next to the text.

- Because we might want to look closer, or keep one word's data displayed while pointing at other things, a "click" should "lock down" the sidebar, so that information doesn't disappear when the cursor hovers over something else. A subsequent click on the token can "unlock" it.
- The site should be entirely self-contained, able to run locally, albeit with the requirement to run a local server. This is why I've included the whole LSJ lexicon-app in `webapps`.
- I'll make an exception for web-fonts, but these should fail gracefully.
- The reader should get the LSJ short-definitions with a "peek" at the sidebar, but there should be a link to the (local) LSJ lexicon. (See "Desidarata" for my thoughts on a subsequent "prepare publication" script.)

Where my earlier attempt is weak:

- Touch-devices don't have `:hover`.
- And in general I gave no thought to formatting for touch or small screens. The `screen-size` thing in CSS and "responsive design" is really complicated to me, and I'd love your help.
- In general, you will know best-practices for formatting of sites of this kind. I would like something that hits a happy medium between "traditional" or "Aldine" and "clean and modern", if that is possible. Your choices thus far show impeccable taste!

### Desiderata

We aren't working on functionality yet, but looking forward…

- "Editor Mode": Say that I am reading a text on these pages with students. As we read, we click on a word and get six possible parsings/lexical-entries for the word. We see which one actually applies in this context ("It is **neuter nominative plural** here!"). I would love to click on that one, of the six, as the "preferred parsing". As we read through the page, some Javascript keeps track of those choices, and before leaving the page invites me to download my choices as a fragment of an "editor's index" in `.tsv` format: CTS-URN \t CITE2-URN (to the morphology dictionary). I'd be on my own to use those `.tsv` fragments to assemble an editor's index file.
- A `prepare_publication.jl` script. This will create a `pub` directory, expected to be temporary, that packages one or more html editions and the files in the `webapps` directory, along with a `README.md`, that will be an easy upload to a server, or easily served locally with *e.g.* `python -m http.server 8080`.
