## Next Step: User Interactions while Reading

This will involve modifying and extending this file: `scripts/generate_html_reader_pages.jl`, along with its attendant JS and CSS files.

The goal:

- A user sees just the Greek text by default. The morphology `div`s are hidden.
- A user interacts with a token by hovering or clicking.
- This displays any morphological-lexical data associated by CTS-URN with that token. by making them visible via CSS and (via JS and CSS) moving them up and near the text. This might require that the reader-page leave an ample margin to the right of the text.
- Since there may be many possible parsings for a given token (`τίνα` has many!), the display of morphology data should scroll.

The example at <https://furman-university-editions.github.io/Readers/Homeric_Hymns/Demeter_1-50.html> was my unaided work, and while it represents my idea of a useful reading environment, it is less than ideal.

What I hope for:

- "Zero-friction" reading: The user should get information on any token (where there is information) with as little interaction as possible. `:hover` should reveal, in a sidebar, lexical and morphological information for a word. This is a "peek".
- Because we might want to look closer, or keep one word's data displayed while pointing at other things, a "click" should "lock down" the view of the data, so that information doesn't disappear when the cursor hovers over something else. A subsequent click on the token can "unlock" it.
- The site should be entirely self-contained, able to run locally, albeit with the requirement to run a local server. This is why I've included the whole LSJ lexicon-app in `webapps`.
- I'll make an exception for web-fonts, but these should fail gracefully.

Where my earlier attempt is weak:

- Touch-devices don't have `:hover`.
- And in general I gave no thought to formatting for touch or small screens. The `screen-size` thing in CSS and "responsive design" is really complicated to me, and I'd love your help.
- In general, you will know best-practices for formatting of sites of this kind. Your choices thus far show impeccable taste!

### Desiderata

This might be the point to consider adding this functionality either now or in a future state:

- "Editor Mode": Say that I am reading a text on these pages with students. As we read, we click on a word and get six possible parsings/lexical-entries for the word. We see which one actually applies in this context ("It is **neuter nominative plural** here!"). I would love to click on that one, of the six, as the "preferred parsing". As we read through the page, some Javascript keeps track of those choices, and before leaving the page invites me to download my choices as a fragment of an "editor's index" in `.tsv` format: CTS-URN \t CITE2-URN (to the morphology dictionary). I'd be on my own to use those `.tsv` fragments to assemble an "editor's morphological index file".
- Related: Currently the pages capture *every possible parsing* of a token. If I can build an "editor's morphological index" documenting the preferred morphology for an instance of a token in its context in the text, I would have the build-script check that dictionary first, and only if a token is not mentioned there, consult the general dictionaries and indices (as we currently do).
